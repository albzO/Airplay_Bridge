## 仍应继续处理的方向

### 1. 优先：协议日志与协议处理分离

`live/protocol.rs:165–179` 在 stderr 读取线程同步输出控制台和文件，之后才在 193 行记录协议状态、在 198 行附近发送 `PCM_READY`。如果控制台或磁盘阻塞，这个线程无法继续解析就绪/故障行或排空 stderr；后端持续输出时还可能产生管道反压。`BackendReader::join` 也没有整体等待期限。

这是源代码可确认的阻塞关系，本轮没有注入慢磁盘复现卡顿。之前修复覆盖 Source、漂移和逐包诊断日志，这条路径仍需处理。

建议把原始协议解析、首因状态和就绪通知留在读取线程，将脱敏后的控制台/文件输出交给有界日志工作线程。保留错误上下文和脱敏规则，明确丢记录数、写入错误与收尾状态。用阻塞/失败 writer 验证 `PCM_READY`、故障识别和取消不受日志影响。最终报告写盘及其他线程仍须单独审查，不能只凭此项声称整个应用有严格停止上限。

### 2. 补齐真实模板的交互回归

当前 `session.test.mjs` 提取并执行 `<script setup>`，mock 桌面 IPC 与浏览器接口；不会渲染 `App.vue` 模板。`App.vue:1166–1178` 的开始/停止/刷新按钮绑定仍未通过实际点击验证。

建议挂载真实模板并 mock Tauri 命令/事件，自动断言：无来源/无设备时不能开始；连接期间来源/刷新受限；停止中不能再次停止或弹出密码输入；密码重试使用新会话；旧会话结束不能恢复按钮或修改新会话。先补这些可模拟的断言，真实 WebView、托盘和键盘行为再单独验证。

### 3. 继续按职责整理采集与视图

当前 `App.vue` 共 1189 行，脚本内容 630 行；`capture.rs` 共 1080 行，`live_selected_diagnosed` 从 533 到 923 行，共 391 行，均含空行与注释。这些数字只用于定位阅读负担。

时间线规则已经独立且有 5 项确定性测试，但采集函数仍组合等待/取包、原始格式解析和声道选择、健康检查、统计/诊断与交付。下一步可以提取纯包解码/声道映射和诊断快照组装，保留 WASAPI 取包/释放的 RAII 顺序。App 可按来源选择、设置和诊断展示拆成组件或 composable；会话控制继续集中管理。不要仅为减少行数拆文件。

### 4. 性能先补测量，再决定 Source 缓冲池

Source 复制仍在，当前合成基线也未测它。建议先扩展无声卡基线，覆盖 Source 订阅交付与左右交换分支，再决定是否增加有界 Vec 回收池。若实现，需覆盖消费者失败、取消、溢出、断开和下一次会话，确保缓冲归还和时长预算一致。

现有基线、比较命令与结果见 [性能基线](performance-baseline.md)。目前默认只报告性能差异，尚无统一固定回归阈值；CI 暂缓期间仍可手动执行显式基线。不能把 Vec 复用计数解释为整机分配次数或 CPU 降幅。

### 5. 保留长期与实机验证边界
